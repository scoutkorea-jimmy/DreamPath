# 04 · 실패 히스토리

## 🟡 해결 · 2026-08-27 · **확장자로 대상을 고른 검사기 셋이 한꺼번에 눈을 감았다**

- **무슨 일**: 관리자 파일을 `.jsx` → `.js` 로 바꾸자 **세 검사기가 동시에** 그 파일들을
  건너뛰었다 — 구문검사 · 이모지 검사 · 인벤토리 생성.
- **가장 눈에 띈 증상**: 인벤토리가 관리자 탭을 **50개 → 0개**로 셌다. 오류는 없었다.
  숫자만 조용히 0이 됐다.
- **뿌리**: 셋 다 `f.endsWith('.jsx')` 로 대상을 골랐다. 그런데 브라우저가 Babel 로
  넘기는 기준은 **파일 이름이 아니라 `<script>` 의 `type` 속성**이다. 검사기가 보는
  기준과 브라우저가 보는 기준이 처음부터 달랐다.
- **더 나쁜 점**: 바로 앞 라운드(v01.101.11)에서 「관리자 앱 전체가 구문검사 밖이었다」를
  고쳤다. **같은 구멍을 이름만 바꿔 다시 팠다.**
- **어떻게 고쳤나**: 셋 다 **HTML 이 실제로 `text/babel` 로 싣는 목록**을 읽는다.
  이름이 아니라 성질이다.
- **재발 조건**: 새 검사기를 만들 때 `endsWith('.확장자')` 로 목록을 만들면 같은 일이
  일어난다. **"브라우저는 이 파일을 무엇으로 판단하는가"** 를 먼저 물어라.
- **교훈**: `rules/04` 의 「권한은 한 곳에서 잠근다」와 같은 성질이다 —
  **이름이 아니라 성질로 목록을 만들어라.** 그리고 이번에는 **검사가 조용히 통과**하는
  형태였다: 0건은 좋은 소식처럼 보인다.

## 🔴 사고 · 2026-08-27 · **리팩터가 함수 본체를 통째로 지웠다 — 관리자 화이트 스크린**

- **증상**: `/admin` 이 완전한 백지. HTML 은 HTTP 200 이고 로컬 파일과 **바이트 단위로 동일**했다.
  전송 계층만 보면 아무 문제가 없다.
- **뿌리**: v01.101.07 에서 컴포넌트마다 네 번 중복돼 있던 `authHeaders()` 를 최상위 하나로
  합칠 때, **기본 헤더를 만드는 본체가 빠지고 자기 호출만 남았다.**

  ```js
  function authHeaders(extra) { return Object.assign(authHeaders(), extra || {}); }
  ```

  → `RangeError: Maximum call stack size exceeded`. React 18 은 렌더 중 예외가 에러 경계에
  잡히지 않으면 **트리 전체를 언마운트**한다. `#root` 가 비었다.
- **왜 배포 전에 못 잡았나**: preflight 의 JSX 구문검사(v01.101.06)는 **파싱만** 한다.
  이 코드는 문법상 완벽하다. **구문검사는 실행검사가 아니다.**
- **왜 늦게 발견됐나**: 배포 성공 · HTTP 200 · 파일 일치 — **정상 신호가 셋이나 있었다.**
  운영자가 화면을 열어 보고 나서야 알았다.
- **어떻게 잡았나**: 헤드리스 브라우저로 **실제 콘솔을 읽어** 스택을 확보했다.
  이 결함은 실행해 보는 것 외에 알아낼 방법이 없다.
- **재시도 조건 / 남은 것**: ✅ **둘 다 v01.101.11 에서 닫았다.**
  - ~~관리자 트리에 에러 경계가 없다~~ → 워치독 + 경계 2단 + 전역 핸들러(세 겹).
  - ~~배포 후 실제 렌더 확인이 없다~~ → `rules/tools/smoke.mjs`, `deploy.mjs` 가 자동으로 돈다.
  - 아직 남은 것: `admin.html` 인라인 스크립트 **500KB 분할**(Babel 이 코드 생성
    최적화를 포기한다는 경고). 동작에는 영향이 없으나 파싱이 느려진다.
- **교훈**: **중복 제거는 「합쳤다」가 아니라 「합친 것이 원래 일을 하는가」로 끝난다.**
  네 개를 하나로 줄인 것은 맞는데, 그 하나가 아무 일도 하지 않았다.

## ⚪ 해결(기계화) · 2026-08-23 · **같은 함정에 세 번 걸렸다 — "KV 만 고치고 코드 기본값을 안 고침"**
| 날짜 | 증상 | 뿌리 |
|---|---|---|
| 8/22 | 내린 상단 배너가 다음 날 화면에 그대로 | KV 만 끄고 `DEFAULT_CONTENT` 는 `true` |
| 8/23 | CUFS 를 지웠는데 **코드 기본값에 84곳** 잔존 | 〃 |
| 8/23 | 레거시 `DreamPath TF` 가 코드 기본값에 잔존 | 〃 |

- **왜 반복됐나**: 8/22 에 이미 "KV 와 코드 기본값 둘 다"라고 **규칙을 적었다.**
  그런데 다음 날 또 걸렸다. → **글로 적는 것만으로는 안 막힌다**는 것이 이번의 진짜 교훈이다.
- **뿌리**: 이 SPA 는 원격 콘텐츠가 도착하기 **전 첫 페인트를 코드 기본값으로** 그리고,
  KV 가 초기화되면 기본값이 곧 라이브 값이 된다. 워커는 KV 원본을 읽으므로 **세 번째 값**
  (worker 상수)까지 있다.
- **어떻게 막았나**: `rules/tools/preflight.mjs` 를 만들어 **배포 전 필수 절차**로 못 박았다
  (`CLAUDE.md` 하드 룰 D-0). 기계가 보는 것:
  ① KV ↔ `DEFAULT_CONTENT` ↔ worker 상수 드리프트
  ② 한 번 지우기로 한 문자열의 부활(파트너 기관명 · 레거시 표기 · 학기 · 박힌 날짜)
  ③ 내려둔 것이 사이트맵 · JSON-LD · llms.txt 에 남아 있는지
  ④ 접수 차단이 **서버에서** 실제로 걸리는지
- **자체 검증**: 만든 직후 `notice.enabled` 를 일부러 되돌려 놓고 돌렸더니 즉시 잡았다.
  첫 실전 실행에서 실제 잔재 **4건**(관리자 학기 라벨 2 · 죽은 파트너 블록 · KV 옛 배너 문구)도 잡았다.
- **남는 한계**: 검사기는 **화면을 보지 못한다.** 지난 회귀 두 건은 둘 다 스크린샷에서
  발견됐다 — 배포 후 실제 화면 확인은 여전히 사람 몫이다.

## ⚪ 해결 · 2026-08-23 · 외부 서비스 상태를 우리 설정값으로 추정했다

## ⚪ 해결됨 · 2026-08-23 · KV 에서 껐는데 화면에는 계속 떠 있었다
- **무엇**: 8/22 에 내린 상단 띠 배너(`🚧 … Official launch mid-June`)가 다음 날 스크린샷에
  그대로 있었다. KV 는 `notice.enabled=false` 로 정상이었다.
- **왜**: 화면에 뜬 문구가 **KV 본문이 아니라 `DEFAULT_CONTENT` 의 문구**였다. SPA 는
  원격 콘텐츠가 도착하기 전 **첫 페인트를 코드 기본값으로** 그린다. KV 만 끄면 그 순간이
  안 막힌다. KV 가 초기화되면 영구히 되살아난다.
- **어떻게 알아챘나**: 다른 작업(문구 교체) 검증용 스크린샷에 우연히 찍혔다.
  **KV 값만 확인하고 끝냈으면 못 봤다** — API 응답이 아니라 실제 화면을 봐야 잡힌다.
- **교훈**: 콘텐츠 스위치를 끌 때는 **KV 와 `DEFAULT_CONTENT` 둘 다** 내린다.
  그리고 **기본값 문구에 날짜를 넣지 않는다** — 코드에 박힌 날짜는 반드시 낡는다
  (`entry_gate` 에서 같은 함정을 이미 겪었다).

## 2026-08-27 · KV 기반 rate limit 은 몰아치는 요청을 절반만 센다

**무엇** `/api/errors` 에 rate limit 을 넣고(KV, 30회/시간/IP) 35회를 연속으로
보냈는데 **전부 통과**했다. KV 카운터를 열어 보니 38회 요청에 `count: 19` —
**절반이 유실**돼 있었다.

**왜** Cloudflare KV 는 read-after-write 일관성을 주지 않는다(최대 60초 캐시).
몰아치는 요청에서는 각 요청이 오래된 값을 읽어 같은 숫자 위에 덧쓴다.

**어떻게 고쳤나** `/api/errors` 는 어차피 같은 요청에서 D1 에 행을 쓴다. 세는
대상이 이미 D1 에 있으므로 `COUNT(*) ... WHERE ip = ? AND ts >= ?` 로 바꿨다
(인덱스 `0042`). 재검증에서 15회 연속 요청이 **15건 전부 차단**됐다.

**아직 KV 를 쓰는 곳 — 재시도 조건**
`rl:signup` · `rl:inq_ip` · `rl:inq_email` · `rl:pwreset_*` · `rl:upload` ·
`rl:msg` · `rl:team_msg` · `totp_confirm` · `totp_verify` 는 그대로 KV 다.
**무력하지는 않다** — 한도가 5~30 으로 낮고, 사람이 1초에 다섯 번 가입하는
경우는 드물며 그때도 절반은 센다. 다만 **정확하지 않다**: 실효 한도가 명목의
1.5~2배로 보아야 한다.
바꿀 만한 조건은 셋 중 하나다 —
① 실제로 그 엔드포인트로 몰아치는 시도가 관측될 때,
② 해당 테이블에 이미 D1 행이 쌓이는 구조라 COUNT 로 대체해도 저장소가 늘지
   않을 때(오류 보고가 그랬다),
③ Cloudflare 가 Workers 에 정식 rate limiting 바인딩을 주는 때.
**아무 근거 없이 전부 D1 로 옮기지 마라** — 로그인·업로드처럼 볼륨이 큰
경로에 COUNT 를 걸면 매 요청에 쿼리가 하나씩 는다.

**배운 것** *한도를 넣었다*와 *한도가 걸린다*는 다르다. **넘겨 보고 막히는지
확인**해야 안다 — 이 건은 "적용했다"에서 끝냈으면 방어가 없는 채로 남았다.

## 2026-08-27 · 방어를 더했더니 사이트가 느려졌다 (같은 날 안에 발견·수정)

**무엇** `/api/analytics` 에 KV rate limit 을 넣었다. 몇 시간 뒤 운영자가
**"홈페이지 반응성이 엄청 떨어졌는데?"** 라고 알려 왔다. 측정하니
`/api/analytics` 가 **1.0~1.5초**였다(`/api/content` 는 0.3초).

**왜** 이 엔드포인트는 **모든 페이지뷰와 클릭이 지나는 가장 뜨거운 경로**다.
거기에 KV **읽기 + 쓰기**를 얹었고, 그 아래에는 원래부터 D1 배치 쓰기를
`await` 하고 있었다. 한 번의 클릭이 KV 2회 + D1 1회를 기다렸다.

**고친 방법** 응답을 먼저 보내고 나머지를 `ctx.waitUntil()` 로 옮겼다.
클라이언트(`analytics-store.js`)는 `sendBeacon` 또는
`fetch().catch(() => {})` 로 보내고 **응답을 읽지 않는다** — 기다릴 이유가
처음부터 없었다. rate limit 도 그 안에 둔다: 이 한도의 목적은 INSERT 를
거절하는 것이지 호출자에게 알리는 것이 아니다.
결과 — `/api/analytics` **1.4초 → 0.25초**, 홈 DOMContentLoaded
**1,157ms → 589ms**. 저장은 그대로 된다(5건 넣어 5건 확인).

**배운 것**
- **뜨거운 경로에 방어를 얹기 전에 그 경로가 얼마나 뜨거운지 세어라.**
  같은 KV 호출이 관리 API 에 있으면 아무도 모르지만, 페이지뷰 경로에 있으면
  모든 방문자가 기다린다.
- **호출자가 응답을 읽는지 먼저 확인해라.** 안 읽는다면 `await` 할 이유가 없다.
- **성능 회귀는 기능 시험을 통과한다.** 200 이 떴고 데이터도 들어갔다.
  운영자의 체감이 유일한 신호였다 — 응답 시간을 재는 습관이 없으면 못 잡는다.
