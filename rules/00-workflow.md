# 00 · 작업 절차

## 0. 세션 시작 (지시를 받기 전)

1. 루트 `CLAUDE.md` 를 읽는다 (자동 로드됨).
2. `ls rules/handoff/ACTIVE-*` — **진행 중 작업이 있으면 그것부터 확인**한다.
   중간에 끊긴 작업을 새로 시작하지 말고 이어받는다.
3. `rules/06-weekly-review.md` 의 "다음 점검일"이 지났으면, 본 작업 전에
   **한 줄로 보고**한다: "주간 점검일이 지났습니다 — 재시도 후보 N건 있습니다."

## 1. 지시를 받으면 — 핸드오프부터 만든다

**코드를 건드리기 전에** `rules/handoff/ACTIVE-<날짜>-<슬러그>.md` 를 만든다
(`handoff/TEMPLATE.md` 복사). 작업이 중간에 끊겨도 다음 세션이 이어받을 수
있어야 한다. 이게 이 절차의 존재 이유다.

- 파일명 예: `ACTIVE-2026-08-22-site-refresh.md`
- 진행 중 **계속 갱신**한다. 특히 다음이 바뀔 때마다:
  - 완료한 단계 (체크박스)
  - 지금 하고 있는 것 (다음 세션이 여기부터 재개)
  - 새로 알게 된 사실 · 막힌 지점
**핸드오프를 안 만들어도 되는 경우**: 질문에 답하기 · 조회 · 한 번에 끝나는
단발 수정(커밋 하나로 끝나고 이어받을 상태가 남지 않는 것). 이때는 히스토리
파일(03/04)에만 남긴다. 판단 기준은 **"세션이 여기서 끊기면 다음 사람이
헤매는가?"** — 헤맬 것 같으면 만든다.

- 한 번에 ACTIVE 는 **하나만**. 새 지시가 오면 이전 것을 `done/` 으로 보내거나,
  아직 안 끝났으면 새 파일과 함께 두되 어느 쪽이 우선인지 첫 줄에 적는다.

## 2. 만들기 전에 — 이미 있는지 찾는다 (스파게티 방지)

새 기능·화면·API·CSS 를 **만들기 전에** 반드시:

1. `python3 rules/tools/build_inventory.py` 로 인벤토리를 갱신하고
   `rules/01-inventory.md` 에서 비슷한 것을 찾는다.
2. 디자인/스타일이면 `rules/02-design-system.md` 를 읽는다.
3. `rules/05-do-not.md` 를 읽는다 — 운영자가 이미 거부한 방향일 수 있다.
4. `rules/04-history-failure.md` 를 검색한다 — 이미 실패한 접근일 수 있다.

**있는 것을 고쳐 쓴다 > 새로 만든다.** 새로 만들어야 한다면 핸드오프에
"왜 기존 것으로 안 되는지" 한 줄을 남긴다. 그 한 줄을 못 쓰겠으면 새로
만들면 안 된다는 뜻이다.

## 2-1. 콘텐츠·설정을 끄거나 바꿀 때 — **세 곳을 본다**

이 저장소에서 가장 자주 반복된 실수다(세 번). 하나만 고치면 되살아난다.

| # | 어디 | 왜 |
|---|---|---|
| 1 | **KV** (`dp_content_v1`) | 지금 라이브 값 |
| 2 | **코드 기본값** (`DEFAULT_CONTENT`, worker 상수) | 원격 콘텐츠 도착 **전 첫 페인트**와 **KV 초기화 시** 이게 이긴다 |
| 3 | **실제 화면** | API 값이 맞아도 화면이 다를 수 있다. 브라우저로 본다 |

`node rules/tools/preflight.mjs` 가 1·2 와 상태 정합성을 기계로 잡아 준다.
3(화면)은 사람이 봐야 한다 — 지난 회귀 두 건 다 **스크린샷에서** 발견됐다.

## 2-2. 외부 서비스는 **양쪽을 따로** 확인한다

우리 설정값(KV·코드)과 **그쪽 등록 상태**는 다른 것이다.
Cloudflare 메일 포워드에서 이걸 혼동해 "인증 링크를 누르세요"라는 **틀린 안내**를 했다
— 실제로는 목적지 주소가 등록조차 안 돼 있었다.
남의 시스템 상태를 우리 설정으로 **추정하지 말고 조회**한다.

## 3. 작업 중

- 배포·커밋·위키 갱신 규칙은 `CLAUDE.md` 하드 룰을 따른다.
- 검증 없이 "됐습니다"라고 하지 않는다. 실제로 돌려보고 결과를 붙인다.
- 운영자가 불편을 호소하거나 "하지 마"라고 하면 **그 자리에서**
  `rules/05-do-not.md` 에 사유와 함께 적는다. 나중에 하려면 잊는다.

## 4. 종료 — 기록을 남긴다 (성공이든 실패든)

| 결과 | 남길 곳 |
|---|---|
| 성공 | `rules/03-history-success.md` 맨 위에 한 항목 |
| 실패·보류·막힘 | `rules/04-history-failure.md` 맨 위에 한 항목 (**사유 + 재시도 조건 필수**) |
| 운영자 금지·불만 | `rules/05-do-not.md` |
| 배포된 버전 | 루트 `HANDOFF.md` + 관리자 위키 (`CLAUDE.md` 하드 룰 0번) |
| 핸드오프 | `rules/handoff/ACTIVE-*.md` → `rules/handoff/done/` 로 이동 |
| 배포 전 | `node rules/tools/preflight.mjs` 통과 + `git status` + 위키 버전 번호 확인 |

**실패를 지우지 마라.** 실패 기록은 다음 사람이 같은 벽에 두 번 부딪히지
않게 하는 유일한 장치다. "이번엔 안 됐다"로 끝내지 말고 **무엇이 참이어야
다시 시도할 만한지**(모델 · 권한 · 절차 · 외부 서비스)를 적는다.
